# Repository agent guidance

Preserve concurrent edits and use an isolated checkout for release work. Keep unrelated desktop, accounting and site changes separate.

## Tammy website releases

For `apps/site` changes or deployment work, read the [Sites release runbook](apps/site/SITE-RELEASE-RUNBOOK.md) and use the [release checklist and record](apps/site/SITE-RELEASE-CHECKLIST.md). Keep commands and current execution evidence there rather than duplicating the full procedure here. Read the current installed Sites skill before using its helpers or native tools.

- **Source and tooling:** `apps/site` depends on `packages/invoices` through `workspace:*`. Use `scripts/site-release.mjs prepare` from the clean, committed repository; never copy only the site folder. The exporter retains the reviewed workspace closure, root dependency/configuration inputs, frozen lockfile and patches. Use the exact Node/pnpm pins in root `package.json` (currently Node `24.18.0`, pnpm `11.15.0`) and validate/build the exported workspace.
- **Descriptor attestation:** finish all source/documentation edits and commit them first. Run the normal `proto:descriptors:evidence` command with `TAMMY_SOURCE_REVISION` equal to that clean source commit; verify before and after its immediate evidence-only child commit. For site-only work, descriptor bytes must stay unchanged. Do not weaken the verifier. The final release candidate is the evidence commit; further source changes require fresh attestation and candidate artifacts.
- **Provenance:** record the exact tested GitHub commit, source/build hashes and Worker archive hash. The configured Sites repository has its own history: a GitHub SHA is not automatically its branch HEAD. Reconcile Sites-only/concurrent edits before pushing. Never assign an old artifact to a new candidate or overwrite another agent's source changes.
- **Supported release flow:** use the installed Sites build/package helpers. `package-site.mjs` packages locally; `site-workflow.mjs` with `archivePath` also commits and pushes source. With authorized source access, use the supported source workflow, then pass its exact pushed Sites commit and matching Worker archive to `save_site_version`. Confirm pushing cannot publish automatically during save-only work. Do not invent deployment endpoints, persist credentials or expand access as a workaround.
- **Existing project:** preserve `appgprj_6a93f33631748191b7c064c033f72b53`, both hosting manifests, null D1/R2 bindings, the public audience and `tammy.tax`. Refresh native Site state before release; do not create a replacement Site. Keep canonical/DNS migration as a separately reviewed release decision.
- **CI boundary:** `.github/workflows/tammy-site.yml` prepares artifacts; it does **not** synchronize Sites source, save a version or automatically publish. Require actual Cuttlefish evidence: `[self-hosted, linux, ARM64, tammy-linux-ci]`, `cf-vm-*`, `aarch64`, and the existing fork guard. A queued job or local pass does not qualify the pool. Do not add a hosted fallback, register runners or change runner security unless that work is authorized.
- **Release gates:** distinguish local checks, Cuttlefish qualification, saved version and production deployment. Record actual browser invoice/quote PDF downloads or print flow, desktop/narrow/mobile checks and touch coverage separately from unit tests. Preparation/save-only requests stop before deployment. Publication and canonical migration need their own requested scope and live acceptance evidence; preserve audience and existing deployment state.

Read current PR/CI/Sites results for each release and retain them in the release record. Keep the PR draft while required runner or release qualification is incomplete; never describe cancelled, pending or skipped checks as passed.
