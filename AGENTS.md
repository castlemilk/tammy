# Repository agent guidance

Preserve concurrent edits and use an isolated checkout for release work. Keep unrelated desktop, accounting and site changes separate.

## Tammy website releases

For `apps/site` changes or deployment work, choose the requested target explicitly. Use the [direct Cloudflare runbook and record](apps/site/CLOUDFLARE-RELEASE-RUNBOOK.md) for the user-requested direct Worker/CI route, or the [Sites release runbook](apps/site/SITE-RELEASE-RUNBOOK.md) and [Sites checklist](apps/site/SITE-RELEASE-CHECKLIST.md) for the existing ChatGPT Sites project. The earlier save-only Sites preparation does not prohibit the subsequently requested direct deployment. Keep detailed commands/evidence in the selected runbook. Read the current installed Sites skill before using Sites helpers or native tools.

- **Source and tooling:** `apps/site` depends on `packages/invoices` through `workspace:*`. Use `scripts/site-release.mjs prepare` from the clean, committed repository (`--target cloudflare` for direct deployment; default `sites`); never copy only the site folder. The exporter retains the reviewed workspace closure, root dependency/configuration inputs, frozen lockfile and patches. Use the exact Node/pnpm pins in root `package.json` (currently Node `24.18.0`, pnpm `11.15.0`) and validate/build the exported workspace.
- **Descriptor attestation:** finish all source/documentation edits and commit them first. Run the normal `proto:descriptors:evidence` command with `TAMMY_SOURCE_REVISION` equal to that clean source commit; verify before and after its immediate evidence-only child commit. For site-only work, descriptor bytes must stay unchanged. Do not weaken the verifier. The final release candidate is the evidence commit; further source changes require fresh attestation and candidate artifacts.
- **Provenance:** record the target, exact tested GitHub commit, source/build hashes and the deployed artifact or Worker archive hash. Do not interchange Sites/direct output or assign a build to another target. The configured Sites repository has its own history: a GitHub SHA is not automatically its branch HEAD. Reconcile Sites-only/concurrent edits before pushing. Never assign an old artifact to a new candidate or overwrite another agent's source changes.
- **Sites release flow:** use the installed Sites build/package helpers. `package-site.mjs` packages locally; `site-workflow.mjs` with `archivePath` also commits and pushes source. With authorized source access, use the supported source workflow, then pass its exact pushed Sites commit and matching Worker archive to `save_site_version`. Confirm pushing cannot publish automatically during save-only work. Do not invent deployment endpoints, persist credentials or expand access as a workaround.
- **Direct Cloudflare flow:** use the verified direct snapshot and `cloudflare-dry-run` / `cloudflare-deploy` wrappers with pinned Wrangler. Deploy `tammy-site-direct` to the verified account's existing workers.dev subdomain; no routes/domain cutover. Require existing approved account/token access and Worker ownership verification. Never initiate login, mint credentials, expand access or enable spending as a workaround. Direct builds exclude Sites deployment metadata while preserving original hosting source files.
- **Existing project:** preserve `appgprj_6a93f33631748191b7c064c033f72b53`, both hosting manifests, null D1/R2 bindings, the public audience and `tammy.tax`. For a Sites release, refresh native Site state; do not create a replacement Site. Keep canonical/DNS migration as a separately reviewed release decision. A direct Workers Custom Domain needs an account-owned active Cloudflare zone; moving tammy.tax from Vercel DNS requires complete record inventory/reproduction and a separately approved nameserver migration, not a registrar transfer or an improvised workers.dev CNAME. Do not add a paid partial-zone plan.
- **CI boundary:** `.github/workflows/tammy-site.yml` prepares Sites artifacts and does **not** synchronize Sites source, save a version or publish Sites. The same workflow's direct Cloudflare job may deploy only through trusted-master push or `workflow_dispatch` with `deploy_cloudflare: true`, using `CLOUDFLARE_API_TOKEN` and account variable only in its deployment step. Pull requests validate without publishing. Existing credentials and runners must actually be available before claiming unattended deployment works. Require actual Cuttlefish evidence: `[self-hosted, linux, ARM64, tammy-linux-ci]`, `cf-vm-*`, `aarch64`, and the existing fork guard. A queued job or local pass does not qualify the pool. Do not add a hosted fallback, register runners or change runner security unless that work is authorized.
- **Release gates:** distinguish local checks, Cuttlefish qualification, saved version and production deployment. Record actual browser invoice/quote PDF downloads or print flow, desktop/narrow/mobile checks and touch coverage separately from unit tests. Preparation/save-only requests stop before deployment. The direct Cloudflare request authorizes that Worker route; it does not authorize a Sites deployment or canonical/DNS migration. Retain the actual direct deployment result and live routes/assets, repeated invoice/quote PDF and mobile evidence; preserve the existing Sites deployment as the tammy.tax fallback.

Read current PR/CI/Sites results for each release and retain them in the release record. Keep the PR draft while required runner or release qualification is incomplete; never describe cancelled, pending or skipped checks as passed.
