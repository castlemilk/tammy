# Local web API

Tammy's browser API is a local development interface over the existing Go accounting core. It serves one encrypted workspace and one active signed-in browser session. It is not a hosted multi-tenant API, and the browser session is not a public API key.

The gateway binds to `127.0.0.1`; its default port is `4174` (`TAMMY_WEB_PORT`). Its expected browser origin defaults to that address and can be set with `TAMMY_WEB_ORIGIN`, for example to the Vite development origin; see [configuration](web-application.md#configuration). Requests must use the gateway's exact Host. A request with a different Origin header or with `Sec-Fetch-Site: cross-site` is rejected with 403. Browser mutations require the configured Origin and `Content-Type: application/json`, optionally with `charset=utf-8`. Non-API GET requests serve the built browser app from `apps/web/dist`. Credentials and response data must not be logged.

## Authentication

Start with `GET /api/session`. This creates a random `tammy_session` HttpOnly, SameSite=Strict cookie when needed and returns `setup`, `recovery` (with the pending `setupId` and, when known, its `expiresAt` deadline), `locked`, or `authenticated`. The gateway rotates the cookie after authentication and retains the core session and organisation context on the server. Financial queries and commands require the authenticated cookie. Client-supplied core authentication or organisation fields are not used to select an account. A successful confirmation or unlock clears every other browser session, so one browser session is signed in at a time.

Until the gateway restarts or the creating browser session expires after 30 minutes without requests, only the browser session that created a pending workspace can confirm it; other sessions receive 403, and another create request receives 409. A confirmation that discards the setup also releases it; see [setup and recovery](#setup-and-recovery).

A newer browser takes over by unlocking. The core unlocks only a locked workspace, so when the core reports the workspace open, `POST /api/workspace/unlock` checks the credentials before it disturbs the signed-in browser. A missing passphrase, username or password returns 400 and changes nothing. The gateway then signs in to the open workspace with the supplied username and administrator password. Wrong ones return 401 with the credentials message under [setup and recovery](#setup-and-recovery) and leave the signed-in browser and MCP as they were. A successful sign-in ends every other core session. The gateway then locks the workspace and unlocks it with the supplied passphrase, so a takeover still needs all three credentials. With a wrong passphrase at that point, the earlier browser has already been signed out and the workspace stays locked until a browser unlocks it. With correct credentials the new browser receives `{ "state": "authenticated", "organisation": … }` with a new cookie, the earlier browser's next API request receives 401 `Start a browser session first.`, and MCP reads follow the new session.

Five failed sign-ins within 15 minutes make the core lock the administrator account for 15 minutes, and a locked account's live sessions stop working too. So after three failed takeover sign-ins within 15 minutes, the gateway answers further takeovers with 429 `resource_exhausted` and `Too many failed attempts. Wait 15 minutes before trying again.` without calling the core, until the earliest of those failures is 15 minutes old. The count is kept in memory and a successful takeover clears it. Unlocking a locked workspace is not limited this way, because the passphrase is checked before any sign-in.

Two timers apply to a signed-in session. The gateway ends a browser session after 30 minutes without API requests; each API request with its cookie, and each authorised MCP request, restarts that timer. The gateway applies the timeout when the next API request arrives, and ending the signed-in session signs it out of the core and locks the workspace. Separately, the core session expires 30 minutes after sign-in or after the last successful write, and reads, including every MCP tool, do not extend it. Once it has lapsed, a read returns 401 `unauthenticated` with `Your session is no longer valid. Unlock the workspace again.`, and the gateway ends the browser session and locks the workspace. Account creation and journal posting report any core rejection, including a lapsed session, as 400 `invalid_argument`.

The gateway keeps at most 64 browser sessions; when it is full, a new session replaces an unauthenticated one, never the session that owns a pending setup. `POST /api/session/logout` accepts `{}` and invalidates the browser session, signs out from the core, and attempts to lock the workspace. A logout from a browser whose session a takeover has already replaced only clears that browser's cookie, so it cannot lock the newer session's workspace. The development server uses loopback HTTP; it is not an HTTPS production session configuration. Do not expose it through a public tunnel or bind it to an external interface.

| Method and route | Purpose |
| --- | --- |
| `GET /api/session` | Obtain browser session and current setup/authentication state |
| `POST /api/workspace/create` | Create encrypted workspace and return the one-time recovery code and its confirmation deadline |
| `POST /api/workspace/confirm` | Confirm saved recovery code, sign in and complete organisation setup |
| `POST /api/workspace/unlock` | Unlock existing workspace and sign in; take over a workspace another browser has open once the credentials are checked |
| `POST /api/session/logout` | Sign out and lock the workspace |

Workspace creation accepts `displayName`, `username`, `workspacePassphrase`, and `administratorPassword`. Confirmation accepts `setupId`, `recoveryCode`, `username`, `administratorPassword`, `businessLegalName`, `businessDisplayName`, and `abn`; resuming setup after a restart may also require `workspacePassphrase`. Unlock accepts `workspacePassphrase`, `username`, and `administratorPassword`. Keep passwords and the recovery code out of browser storage and saved request examples.

### Setup and recovery

`POST /api/workspace/create` returns `{ setupId, recoveryCode, expiresAt }`. `expiresAt` is the core's deadline for confirming the recovery code, 15 minutes after creation, as an ISO 8601 UTC string such as `2026-11-10T06:10:00.000Z`; the core keeps whole seconds. While the setup is pending, `GET /api/session` returns it with `setupId`. It is absent once the code has been accepted, and for a setup recorded before the gateway kept deadlines.

The gateway checks the setup details before calling the core. A username with leading or trailing spaces returns 400 `invalid_argument` with `Remove the spaces at the start or end of the username.` The workspace passphrase and the administrator password must follow the core's rule: at most 1024 bytes of UTF-8, then 15 to 128 characters after Unicode NFC normalization, each a letter, mark, number, punctuation mark, symbol or the ASCII space. Otherwise the response is 400 `invalid_argument` with `The workspace passphrase must have 15 to 128 characters: letters, numbers, punctuation, symbols or spaces.`, or the same message for `The administrator password`. The core checks the administrator password only after it has reserved the setup's files, so checking it first keeps a rejected password from leaving a workspace file behind. This local core loads no common-password list. The setup form asks for 16 to 128 characters.

If the data folder already holds `core/workspace/tammy-workspace.db` while the gateway has no setup record, for example because the core finished a create after the request timed out, the core would refuse to create another. The response is 409 `conflict` with `This data folder already holds a workspace that this web server has no record of. Stop the server, move the folder aside or set TAMMY_WEB_DATA_ROOT to a new folder, then start again.` A validation fault the core still reports after these checks returns 400 `invalid_argument` with `The core refused to create the workspace. Restart Tammy and try again.` A create request while a workspace or a pending setup exists returns 409 `conflict`.

When the core rejects a pending confirmation, the gateway checks these cases in order:

1. The core had already confirmed this setup, for example when a confirmation is retried after a restart without the workspace passphrase. The gateway records the confirmation instead of counting a wrong code, unlocks the workspace with the supplied `workspacePassphrase` if the core reports it locked, and continues with sign-in. A missing passphrase then returns 400 `Enter the workspace passphrase.` and a wrong one returns 401 `The workspace passphrase is incorrect. After 5 failed attempts, wait 15 minutes before trying again.`
2. The deadline has passed. The response is 409 `conflict` with `This setup expired before it was confirmed. Start setup again.`
3. Otherwise the recovery code was wrong. The gateway counts it in `web-workspace.json`, so the count survives a gateway restart. The first four incorrect codes return 400 `invalid_argument` with `The recovery code does not match. 4 attempts remain before this setup is discarded.`, counting down to `1 attempt remains`. The fifth returns 409 `conflict` with `This setup was discarded after 5 incorrect recovery codes. Start setup again.`

After either 409 the setup is gone. The core has no operation to cancel a pending setup, so the gateway first sends five deliberately invalid confirmations, with a code outside the recovery alphabet, which make the core discard the pending setup and delete its files. The gateway then deletes `web-workspace.json` and releases the creating browser's ownership. Some rejections, such as one while the core is reconciling the setup, do not count toward the core's discard. If the workspace file is still there after the five confirmations, the gateway keeps the setup and returns 409 `conflict` with `The core has not discarded this setup yet. Restart Tammy, then try again.` `GET /api/session` returns `setup`, and any browser can create a workspace again.

If the core accepts a confirmation but reports the workspace locked, which happens when a retried confirmation replays one the core completed before a restart, the gateway unlocks it with the supplied `workspacePassphrase` before signing in. A rejected sign-in during confirmation returns 401 `The username or administrator password is incorrect. After 5 failed attempts, wait 15 minutes before trying again.` The setup stays confirmed, so the next confirmation does not check the recovery code with the core again and retries the sign-in.

`POST /api/workspace/unlock` returns 401 `unauthenticated` with `The workspace passphrase, username or administrator password is incorrect. After 5 failed attempts, wait 15 minutes before trying again.` when the core rejects the passphrase or the sign-in. After five failures within 15 minutes the core refuses unlock or sign-in for 15 minutes, with the same response. A failed sign-in locks the workspace again. A missing passphrase returns 400 `Enter the workspace passphrase.`, and a missing username or password returns 400 `Check the supplied details and try again.` For an unlock of a workspace another browser has open, see the takeover rules under [authentication](#authentication). The message `Your session is no longer valid. Unlock the workspace again.` is reserved for signed-in requests whose core session the core no longer accepts.

## Accounting routes

| Method and route | Request / result |
| --- | --- |
| `GET /api/overview` | Attention counts and source references |
| `GET /api/accounts` | Account list |
| `POST /api/accounts` | `idempotencyKey`, `code`, `name`, `type`; returns created account |
| `GET /api/journals` | Journals with lines and account names |
| `POST /api/journals` | `idempotencyKey`, `date`, `description`, `lines`; returns posted journal |
| `GET /api/trial-balance?asOfDate=YYYY-MM-DD` | Trial balance and exact debit/credit totals; defaults to today's Melbourne date |
| `GET /api/documents` | Retained document review records |
| `POST /api/documents/upload` | `idempotencyKey`, `sourceDisplayName`, `mimeType`, `originalBase64`, optional `extractedText` and `candidate`; retains document for review |
| `POST /api/documents/:id/review` | `idempotencyKey`, `version`, supplier/reference/date and subtotal/GST/total amounts; returns reviewed document |
| `GET /api/banking` | Imported statement lines and independent banking summary |
| `POST /api/banking/import` | `idempotencyKey`, `openingBalanceMinor`, `lines` with `date`, `description`, `amountMinor`; returns the import `id` |
| `POST /api/banking/:id/match` | `idempotencyKey`, `version`, `reference`; returns matched line |
| `POST /api/banking/reconcile` | `idempotencyKey`; returns completed reconciliation count and balance |
| `GET /api/bas` | Current workpaper, or `workpaper: null` |
| `POST /api/bas` | `idempotencyKey`, `periodStart`, `periodEnd`, both within calendar 2024; returns draft workpaper |
| `GET /api/insights` | Deterministic attention suggestions derived from core records |
| `GET /api/capabilities` | API, MCP, intelligence and reporting availability/boundaries, including the organisation's tax-rule bundle reference |

Journal lines carry `accountId`, `description`, `debitMinor`, and `creditMinor`. Document reviews carry `supplierName`, `invoiceNumber`, `date`, `subtotalMinor`, `gstMinor`, and `totalMinor`. Account creation currently accepts `asset`, `liability`, `equity`, `income`, or `expense`. Account reads can also report `other_income`, `other_expense`, `contra` or `unknown`.

Uploads accept PDF, PNG and JPEG with matching file signatures, at most 512 KiB decoded. `originalBase64` must be canonical base64. Optional extracted text is limited to 32 KiB; it is supplied text, not a promise of server OCR. Candidate fields use the document-review shape and remain subject to human review. JSON request bodies are capped at 768 KiB; the 512 KiB file limit keeps a base64 upload within that cap and the core's 1 MiB message limit. Retention and review do not create accounting postings.

The browser attempts bounded extraction of uncompressed native PDF text operators before upload. This is not a general PDF renderer, font decoder or OCR engine. Images and unsupported PDF content need manual entry. The review screen has no source-file preview; currently extracted text is visible immediately after upload, rather than fetched back as a source-preview API.

## Exact values and replay

Money is AUD integer cents. Inputs accept safe JSON integers or canonical decimal integer strings within signed 64-bit range. Outputs use a JSON number when safe and a decimal string otherwise. Consumers must support both forms without converting large strings through JavaScript `Number`. Dates are valid calendar dates in `YYYY-MM-DD` form. Resource IDs and operation keys are canonical UUIDv7 values; optimistic versions are positive integer values, preferably decimal strings.

Financial command requests carry an `idempotencyKey`. Generate it once when the user submits an operation, and never generate a fresh key merely because a network failure left the outcome unknown. Manual journal posting uses core idempotency: retrying the unchanged command with its original key returns the retained journal. Reusing a key with a different command returns 400 `invalid_argument` with the same message as a validation failure, `The core rejected these details. Check them and try again.`, so the response does not show which of the two happened. After an uncertain earlier attempt, inspect the journal list before editing the request or choosing a new key. A changed key represents new intent and can create a second posting.

Replay guarantees are operation-specific. The current document-review and bank-line-match handlers require a command context but rely on `version`, not retained idempotency results. After a successful write, repeating their old version returns a conflict. Refetch the record after an uncertain response and inspect its state before deciding whether another action is required. Do not assume every route has the same replay guarantee as journal posting.

The gateway derives each journal line's `clientLineId` from the operation key and line position, so a retry sends the same command; the core assigns journal and line IDs and returns the retained journal on replay. The core checks balancing, account permissions, versions and posting constraints. Browser totals are previews, not accounting authority. Reviewing a document does not post a journal. Matching a bank line does not complete reconciliation. A BAS workpaper is always a draft and is never lodged.

Errors use an `error` object with a safe `message` and stable `code`: `invalid_request` or `invalid_argument` with HTTP 400, `unauthenticated` with 401, `forbidden` with 403, `not_found` with 404, `conflict` with 409, `request_too_large` with 413, `resource_exhausted` with 429, or `internal` with 500. A conflict requires examining the current record/operation before changing or retrying it; it is not a reason to generate a fresh key and blindly repost.

## Read-only MCP

The MCP server uses stdio. It is separate from the desktop's [local API and MCP](local-api-mcp.md): it uses no connection file, reads only this gateway's workspace, and has no resources or invoice proposal tool. Set the same secret `TAMMY_MCP_TOKEN` of at least 32 characters on the gateway and MCP process, and set `TAMMY_WEB_PORT` to the gateway's port if it differs from 4174. Configure the MCP client to launch `mise exec -- pnpm --silent --dir /absolute/path/to/tammy/apps/web mcp`, substituting the repository path. The `--silent` flag keeps package-manager status output out of the protocol stream. Supply the token through the client's environment configuration; never put a real token into documentation, command-line arguments or a browser page.

The tools are `get_overview`, `list_accounts`, `list_journals`, `get_trial_balance`, `list_documents`, `list_bank_lines`, `get_gst_workpaper`, and `get_insights`. `get_trial_balance` accepts optional `asOfDate`; other tools take no arguments. All are marked read-only and call a fixed query allowlist. They cannot create workspaces, authenticate users, post journals, modify documents or invoke arbitrary core methods.

Each tool calls `GET /api/mcp/<name>` on the gateway, where `<name>` is `overview`, `accounts`, `journals`, `trial-balance`, `documents`, `banking`, `bas` or `insights`, with an `Authorization: Bearer` header carrying the token. These endpoints ignore the browser cookie and return the same JSON as the matching browser route for the active session. A wrong or missing token, an unknown name, a `HEAD` request, a gateway without a token, or no unlocked browser session returns 401. Other methods are rejected too: without the configured Origin and a JSON content type they fail the earlier request checks with 403, and otherwise they return 401. A wrong Host, a different Origin or `Sec-Fetch-Site: cross-site` also returns 403.

The adapter returns the gateway's JSON as text content, retaining exact money values and list-bound metadata. A gateway 4xx response other than 401 that carries an `{ "error": { "code": …, "message": … } }` body becomes an `isError` result with the text `<code>: <message>`; for example, `get_trial_balance` with `asOfDate` `2024-02-30` returns `invalid_argument: Use a valid date in YYYY-MM-DD format.` A 401, a 5xx, or a 4xx without that body returns `Tammy is unavailable or the local workspace is not authenticated.`, and a network failure or a response that is not JSON returns `Could not reach the local Tammy gateway.`

MCP requires both the configured token and an active authenticated browser workspace. It follows that single workspace; there is no tenant selector. Logout or session expiry removes that access, as does a takeover that signs the earlier browser out but then fails on the passphrase. A takeover with wrong credentials leaves MCP as it was, and after a successful takeover MCP reads the new browser's session. Each authorised MCP request keeps the signed-in browser session from idling out, but MCP tools are reads, so they do not extend the core session; see [authentication](#authentication). This is a local stdio integration; there is no public remote MCP endpoint or OAuth/API-key lifecycle in this release.

## Current bounds

List reads request at most 200 records and return `page: { limit, returnedCount, mayHaveMore, cursorSupported }`. `mayHaveMore` is conservatively true when 200 rows were returned; it is not an exact total. The gateway reads only the first page and reports `cursorSupported: false`: the core rejects continuation cursors for accounts, journals and bank lines, and although it returns a next cursor for documents, the gateway does not request later pages. Do not treat a full 200-row list as exhaustive or derive financial totals from it; use the trial balance and banking summary projections. The core attention projection currently counts all retained records, including `currentDraftBasWorkpapers` and the fields whose protobuf names end in `InPeriod`; these are not verified period-filtered analytics.

Overview `basStatus` names the core's BAS preparation attention status for the reporting period the gateway requests, which is the current calendar year in Australia/Melbourne: `unspecified`, `not_created`, `draft_not_lodged`, `outdated`, `action_needed`, `review_ready`, `frozen_for_manual_handoff`, `external_confirmation_recorded` or `disputed`. It describes BAS preparation, which the web cannot create or advance, not the GST draft. The current core reports `not_created` or one of `action_needed` through `disputed`; no current core code path reports `draft_not_lodged` or `outdated`. Without a BAS preparation period for the requested dates the core reports `action_needed`, so a web workspace reports `action_needed` whether or not it has a GST draft. Use `currentDraftBasWorkpapers` or `GET /api/bas` to check for a draft.

`POST /api/bas` accepts any `periodStart` and `periodEnd` within calendar 2024 (1 January to 31 December 2024), not only quarters, with the start on or before the end. Other periods return 400 `invalid_argument` with `The period must start and end within calendar 2024, with the start on or before the end.`, and the browser checks the same rule before sending. Calendar 2024 spans the second half of AU tax year 2024 and the first half of tax year 2025. The core itself checks only that the dates are valid and in order. The desktop gates drafts through the core's reporting-capability registry instead, by the tax year of the period end, for AU tax years 2024 to 2027: periods ending from 1 July 2023 to 30 June 2027. The `reporting.year` value 2024 in `GET /api/capabilities` is the web's calendar-year gate, not a tax year.

The gateway returns a subset of the core workpaper: `id`, `status` (always `draft_not_lodged`), `periodStart`, `periodEnd`, `gstCredits1bMinor`, `sources`, `candidateGstMinor`, `candidates`, `sourcesChanged`, `reviewWarnings` and `limitations`. `salesG1Minor`, `gstOnSales1aMinor` and `netGstPayableMinor` are always `null`: the core calculates them, but the gateway does not return them or the core's invoice sales sources, and the browser has no invoice workflow. In the current core, `gstCredits1bMinor` counts only GST claimed through purchase postings, which this API cannot create, and `sources` lists the purchase sources behind it. A reviewed document without a purchase posting is a provisional candidate, not a credit. `candidates` lists every such document whatever its date, including documents outside the draft period and undated ones (`date: null`), and `candidateGstMinor` is the core's total for all of them, not a period subtotal. For example, a draft for 1 April to 30 June 2024 with reviewed documents dated 12 May 2024 ($29.00 GST) and 1 September 2025 ($1,000.00), and one undated ($0.50), reports `candidateGstMinor` 102950. A candidate's supplier and invoice details come from the current document list and are blank when that document has changed since the draft or is not among the first 200 documents. For a workpaper saved before the core's reconciled purchase format, `sources` holds its reviewed-document credit lines and `candidateGstMinor` is `null`. `limitations` states that sales, GST on sales and net GST are not shown and, for the reconciled format, what the candidates are. The workpaper does not provide a complete BAS, BAS preparation, declaration or ATO lodgement. Insights are deterministic rules, not model predictions. This release has no remote bank feeds, public API keys, tenant selection or autonomous financial mutation.

“Current workpaper” means the latest retained draft. The core recomputes `sourcesChanged` on every read of it: the flag is true when the current source fingerprint differs from the one saved with the draft, for example after another document is reviewed, and also, with a warning added, when the GST basis history needs review or the current sources exceed the workpaper's capacity. `reviewWarnings` carries up to 10 of the core's warning strings verbatim, such as a note that retained purchase review rows include legacy candidates. The draft's figures and candidate list stay as retained; create another draft to include later changes. Do not infer freshness from the draft's presence or the Overview draft count.

`GET /api/capabilities` reads the organisation from the core. `reporting.taxRuleBundle` is the organisation's active tax-rule bundle reference, `{ id, revision, contentHash }` with the revision as a decimal string and the hash as lowercase hex, or `null`. Like other reads, this route returns 401 once the core session has lapsed.

The implementation source is `apps/web/server/gateway.mjs` for routes, sessions, takeover and MCP endpoints, `apps/web/server/security.mjs` for Host and Origin checks, `apps/web/server/errors.mjs` for the HTTP status to error-code contract, `apps/web/server/facade.mjs` for validation, setup and recovery handling and protobuf mapping, `apps/web/server/main.ts` for configuration and core supervision, `apps/web/server/mcp.ts` for the MCP adapter, `apps/web/src/api.ts` for the browser client, and the generated schemas in `packages/connect-client/src/gen/tammy/v1/` for core contracts. The browser DTO layer deliberately exposes only the connected subset; changes should update server mappings, browser types, contract tests and this document together.
