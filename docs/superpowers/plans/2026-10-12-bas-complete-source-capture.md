## Current shape and boundaries

The source readers are complete individually, but there is no combined producer in internal/baspreparation and no production call to CalculationRepository.Append. The existing CreateBasDraft route in internal/localproduct/ledger_sqlcipher.go opens a serializable encrypted transaction, authorizes inside it, then calls reporting.CreateBASDraft with the same executor. Its collectBASSources in internal/reporting/bas_sources.go is period-oriented and intentionally reduces source detail to the saved-workpaper projection. Preserve that path and its current financial/tax revision behavior; do not reuse it as complete coverage.

The accepted module-owned read APIs are:

- Purchases: purchases.Repository.CaptureCoverageForBASWithPayloadBudget(ctx, organisationID, maximumPayloadBytes) returns complete modern postings, document/opening roots, legacy history and linked accounting proofs. It is all-organisation and period-independent, exposes PayloadBytes and ReceiptCount, and already supports a caller budget.
- Invoices: invoices.ReportingPort.CaptureBAS(ctx, organisationID, period) returns all invoice states and histories with issue-date disposition kept separate from receipt timing. It includes posting lines, receipt allocations and unique journal proofs. Its result currently has no PayloadBytes field or caller-budget variant.
- Accounting: accounting.JournalRepository.CaptureTaxFactsForReporting(ctx, organisationID) returns every signed tax fact, including SQL NULL source-hash presence, exact rule references and complete parent journals. JournalRepository.GetForReportingWithPayloadBudget covers journals without facts. The fact capture result currently has no PayloadBytes field or caller-budget variant.
- Rules: artefacts.Repository.GetForReportingWithPayloadBudget(ctx, organisationID, source, budget) validates one exact active tax_rule_bundle and its full catalogue, without making period or eligibility decisions.
- BAS scope: ProfileRepository.GetCurrent/GetExact, PeriodRepository.GetCurrent/GetExact, and SavedPaygRepository.GetExact read the exact retained obligation/profile/period and PAYG input records. organisations.Repository.Get supplies the current organization version and active rule reference.

All these repositories accept the same caller-owned executor. Purchase, invoice and accounting each enforce their own 1,000-row / 8 MiB bounds, but the combined source-root/receipt count, one cross-module 8 MiB reservation, and aggregate retained-byte reports are not currently exposed. BasCalculation.Coverage is capped at 1,000. Before implementation, resolve this API gap explicitly: the recommended contract is one combined root/receipt count and one combined source-payload budget, reserved before source-body hydration. Add additive count/size preflight or caller-budget capture variants to invoice/accounting as needed; do not estimate SQL retained bytes from protobuf sizes or stack independent module budgets and call them one bound. Preserve each module's existing default API behavior.

## Capture and source-currentness design

Create services/core/internal/baspreparation/sources.go with a typed coordinator and typed capture result. Inject small module-owned interfaces so tests can provide bounded records without SQL while production constructors pass the same executor-backed repositories. The coordinator owns ordering, source fingerprint framing, source-to-coverage mapping, cross-module deduplication, and aggregate limits. It must not query private module tables to reconstruct fields those modules already own.

Capture the current organization, exact BAS profile and confirmed period references, active tax_rule_bundle, selected PAYG input, and all module captures through the same serializable transaction. The period supplies downstream classification dates; it must never reduce invoice, purchase, tax-fact, or legacy-history census scope. The source readers return no partial object on cancellation or bound failure. The coordinator must return no partial combined result either and must never begin or finish a transaction, write a workpaper/calculation, or bump a source revision.

Retain the complete revision vector from the financial revision row (`financial_revision`, `ledger_revision`, `settlement_revision`, `banking_revision`, `tax_source_revision`, `organisation_profile_revision`, and `rule_bundle_revision`), plus the exact PAYG-input, BAS-profile, and confirmed-period revisions represented by `BasSourceRevisionVector`. Preserve and hash the complete vector for historical metadata integrity (`RevisionVector` / `RevisionVectorHash`), but define a separate, tagged source-currentness projection that omits the aggregate `financial_revision` and includes only the source-domain counters and exact scope refs relevant to this capture. The aggregate counter is intentionally coarse: `revisions.Repository.Bump` increments it for every selected domain (see `internal/revisions/repository.go:114-130`), even when the domain-specific counters for this BAS source set do not change. Including it in `SourceSnapshotHash` or comparing it for freshness can mark identical retained sources stale after a report-only or otherwise unrelated revision bump. The module fingerprints and source-specific revision counters are authoritative; do not treat a revision counter alone as a source-content proof. Report-only events remain outside the source fingerprint. Use the current organization's exact active rule ref and fail closed if its type, revision, or hash cannot be read by the artefacts-owned reader.

The existing saved-workpaper path confirms this separation: `internal/reporting/bas_sources.go:21-22` explicitly describes its source fingerprint as independent of `financial_revision`; lines 114-135 hash the captured workpaper source fields and purchase fingerprint, not the global counter. `Repository.GetCurrentBASDraft` at `internal/reporting/bas_repository.go:255-265` marks saved sources changed by comparing that fingerprint, not revision counters. `taxHandler.CreateBasDraft` at `internal/localproduct/ledger_sqlcipher.go:481-505` saves through a caller-owned transaction and currently makes no call to a revision-bump helper. The adjacent comment in `bas_sources.go:21-22` says creating a workpaper itself changes the global revision, so that comment and the current route behavior should not be used as a substitute for the source-content currentness rule. The combined currentness comparison must use the explicit source-relevant projection and source fingerprints, rather than the full retained revision-vector hash.

Keep complete source identity distinct from source classification. Preserve raw source IDs and nullable original revision/hash through BasRawSourceRef; use computed hashes only at their declared proof scope. Attach complete journal, invoice, purchase, document, evidence, rule, tax-fact, and line/allocation references in ordered lineage/evidence identities. A reference-only proof must not claim that the referenced body was loaded.

## Candidate mapping, deduplication, and calculation

Map every source family to typed BasSourceCoverage rows and stable dispositions. Keep date semantics separate: invoice issue date, payment date, evidence-held date, purchase claim period, and confirmed statement period are not interchangeable. An issued-but-unposted invoice remains an explicit blocker; a draft remains visible with a clear excluded explanation; zero/unpaid sources remain represented; future, old, and undated purchase evidence stays discoverable. An unclassified manual tax fact is a typed blocker. Never infer GST direction or timing from sign, account code/name, or journal date. A source classification requires a supported immutable reviewed fact and rule.

Deduplicate financial effects in the producer using domain keys that include a source row and its component where needed (for example, tax-fact row, payment allocation, purchase allocation, or invoice income-line sequence). Evidence-only documents enrich lineage and do not create a second candidate. Deduplicate accounting journal proofs by exact journal identity and retain each complete proof once. Do not impose generic repository uniqueness on repeated SourceRef identities: one posting may legitimately support multiple distinct line/classification candidates, and schema 13 only keyed the candidate manifest by sequence. Keep candidate-level conservation tests in the producer.

Resolve one disposition per effect. A candidate may be eligible only when the active GST basis, exact supported rule, evidence/claim timing, posting or settlement, and retained review facts establish the treatment. Keep exclusions and unresolved/unsupported reasons plus supporting identities in coverage. Do not let manually entered totals override computed GST.

Reconcile period amounts without double-counting the invoice and its receipts or an expense and its settlement. Assert exact G1/1A/1B calculations against line, allocation, cash-flow, payable, deferral, suspense and tax-fact components. Deferral resolves only the identified period decision and leaves future obligations/deadlines visible. Feed exact eligible aggregates to the existing integer/rational calculator; incomplete or unsupported source decisions remain in coverage and block a complete outcome.

Order coverage deterministically by source family, exact identity, component key, and disposition with a documented stable tie-breaker. Compute the coverage-manifest hash over the ordered full bodies. Compute `SourceSnapshotHash` over a tagged deterministic encoding of organization/profile/period/rule/input refs, module fingerprints, the source-relevant revision projection (excluding aggregate `financial_revision`), all candidate dispositions, and evidence identities. Exclude audit/report-save events. Compute `RevisionVectorHash` over the full retained vector, including `financial_revision`, for historical integrity; do not use it as the currentness gate. The final `BasCalculation` must bind both hashes and exact refs, the rule/calculator/form versions, full revision vector, result, workpaper snapshot, and complete ordered coverage before `CalculationRepository.Append` verifies and retains it.

## Required native regressions

- Candidate and receipt combined limits at exact limit and limit+1; oversized combined bytes at exact budget and budget-1; assert overflow happens before any body/payload query and returns no capture.
- Old/future/undated, draft, issued-unposted, unpaid, zero-value and paid invoices; receipts before/within/after the target period remain represented with exact date semantics.
- Modern purchases, reviewed and NEEDS_REVIEW documents, promoted historical review sources, POSTED/REPLACED openings, stale unpaid review after a new payment, prior-only journal and manual payment edges; no duplicate credit or receipt.
- Every tax fact state/treatment/sign/source kind, NULL source hash versus present zero/revision/hash, source-only changes with unchanged money, exact rule/catalogue proof, and unsupported manual fact blocker.
- Same exact line/journal reused as lineage without duplicate retention; two distinct allocations/lines on one parent remain separate financial effects.
- Current profile, period, active rule, PAYG input, and each source-relevant revision-vector field independently invalidate the source snapshot. A `financial_revision`-only bump with identical sources must leave source freshness and `SourceSnapshotHash` unchanged while the retained full vector and `RevisionVectorHash` change. Report/audit-only additions do not.
- Cancellation at each module boundary, caller rollback/reopen, caller work survives append/savepoint failure, no changes to SQL total_changes or financial/source revisions.
- Reconciliation fixtures for cash/non-cash basis, partial invoice receipts, prior-period purchase paid this period, evidence timing, deferral/suspense conservation, and one real unclassified manual-tax blocker.
