# BAS legacy support currentness and reversal cash discovery

Status: accepted after specification/quality re-reviews, focused/complete affected native race, real TLS, default Core and pinned production-build gates (2026-10-16). The [implementation plan](../plans/2026-10-15-bas-legacy-currentness.md) records exact evidence and model fallback. This is a dependency of [complete source capture](../plans/2026-10-12-bas-complete-source-capture.md), after modern purchase nomination in `a8c6e7d0`; legacy nomination and the combined producer remain open.

## Scope and success criteria

Pin the existing legacy classifier's current-owner predicates before introducing any pre-body nomination selector. Use real document, purchase, journal, reversal, evidence and account writers. A retained review is immutable history; its source identity, explicit support hashes and current contextual cash facts are separate proofs. Journal version alone cannot prove either its canonical content or the current classification of its accounts.

The regression hypothesis is that `legacyJournalPayments` finds direct document/opening source IDs and tax-fact source IDs, but misses a no-tax-fact reversal whose source ID is its original journal ID. Its existing cash predicate accepts current POSTED manual journals other than OPENING, including a REVERSAL when another source path discovers it. Follow verified reciprocal reversal lineage consistently for direct and tax-fact source roots. Only an actual current cash-credit line establishes a known payment; expense recognition, an obsolete reversed journal and a cash debit do not.

For a valid evidence-only linked document, cash credit reversed into cash debit leaves the source suppressible when no other contradiction exists. Cash debit reversed into cash credit makes the source unresolved and prevents exclusion. The same predicates apply to explicit payment support and unpaid-through-balance checks. Retain immutable reviews and exact current payment hashes; preserve the period/balance checks already owned by the classifier. Full coverage must still retain both complete journal bodies and reciprocal links.

## Smallest implementation

First reproduce both directions with native writer/full-reader tests. If the hypothesis is confirmed, reuse the existing purchase-owned `purchaseCoverageJournalClosure` for the already discovered roots rather than writing another recursive SQL query or a second link validator. Its same-owner, reciprocal version/source, acyclicity and discovery-byte checks apply before this helper hydrates closure bodies. Keep a 1,000-journal bound on the complete unique set of roots and all linked ancestors/descendants, and deterministic ID order. `LegacyCandidates` already hydrates direct-root prior-source proofs separately; this change does not establish a whole-request pre-body fence or reorder that existing path.

The legacy family is stored `source_kind=0`, which includes MANUAL, REVERSAL, OPENING, RECEIVABLE and legacy BANKING source types; the protobuf REVERSAL enum is distinct from MANUAL. Allow valid kind-0 reversal descendants, retain OPENING proof ancestors but exclude them from current payments, and reject malformed or nonzero workflow-owned closure nodes rather than silently skipping them. Preserve existing direct roots, including valid kind-0 RECEIVABLE/BANKING rows. No transaction lifecycle or write belongs to this read.

An explicit retained payment ref can now identify an indirectly linked current reversal. Complete coverage must verify its source-specific ancestry through the already captured, verified journal closure rather than requiring the leaf itself to be a direct source edge. Bound the backward walk by the captured journal count, require same-owner kind-0 proofs and reciprocal source/version links, and end at an exact direct prior ID of this legacy source. A globally captured journal belonging only to another source cannot satisfy this proof. Keep `PriorJournalIDs` and receipt fields unchanged. Preserve the existing exact support version/hash check and historical POSTED-body reconstruction after the supported reversal is itself reversed; ancestry never substitutes for a body hash.

Alternatives considered: a new recursive SQL lookup would duplicate the accepted closure validation; a new decision-selector API would introduce unreviewed reservation and policy changes before the existing predicate is pinned. Both are deferred. No production fix is accepted solely from static analysis.

The root/receipt census intentionally excludes reversal lineage. Do not alter `BASScalarKey`, `IsReceipt`, coverage receipt counts or direct physical-key scope to implement the classifier's current cash predicate. Full journal closure is retained by the complete reader. This checkpoint does not introduce nomination selectors, a pre-fence decision-proto stage, new body hashes, contracts, migrations, global fences or the combined producer.

## Verification

Native tests must inspect real writer results and retained SQL linkage, prove no tax fact supplies an accidental alternate path, exercise both reversal signs and a reversal-of-reversal, and compare exact full coverage bodies. Explicit depth-one/two reversal support must round-trip through the real review writer and complete capture, including after its later reversal. Structural graph tests must reject unrelated captured chains, missing/foreign/nonzero-kind parents, nonreciprocal or wrong-version edges, cycles and wrong support hashes. Currentness oracles should additionally pin current account classification independently of an unchanged journal hash/version and evidence withdrawal independently of the legacy source/link identity where existing tests leave a gap. Reuse existing history/conservation helpers, with no writes, revision drift or caller transaction lifecycle from readers.

Run focused native RED before a production fix, then focused native race, complete affected purchase/accounting/reporting native race, existing real TLS journeys, default Core tests and the pinned production build. The previously accepted expensive 1,000-public-posting fixture may remain the sole broad-suite exclusion; no new regression may be skipped. Independent specification review precedes quality review. Record actual evidence and leave overall Task 5 open.
