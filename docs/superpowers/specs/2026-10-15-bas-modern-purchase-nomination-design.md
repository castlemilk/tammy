# BAS modern purchase structural nomination

Status: accepted after independent GPT-6 Luna Max design/specification/quality reviews, focused/complete affected native race, existing-route TLS, default Core and pinned production-build verification. The [implementation plan](../plans/2026-10-15-bas-modern-purchase-nomination.md) records exact evidence. This dependency nominates modern posting/payment components only; it is not the complete purchase candidate set or the cross-module union.

## Decision

Retain every modern posting allocation and every payment allocation as a structural coverage unit. If a posting has no allocation children, nominate its posting fallback; if a payment has no allocation children, nominate its payment fallback. Never nominate parent money alongside its child components. Both families remain discoverable on either retained GST basis, including zero, old, future, unpaid and partly paid sources. Full verified retained facts later choose additive roles and dispositions. Posting coverage can retain unpaid/deferred obligations while payment coverage represents settlements; these are not two additions of the same GST.

Deferrals, portions, attributions, evidence, events, documents, reviews, opening context and linked manual journals remain physical proof/history. Repeated immutable decisions over the same source do not add another modern candidate. Their complete classification and proof attachment remain later requirements. Evidence-only legacy suppression cannot be derived from a review disposition/link alone: complete support or payment facts may instead yield an unresolved source. A conservative legacy upper bound cannot replace an exact union.

Alternatives are a new pure mapper revalidating all 15 families, or retained-basis-specific nomination with additional selectors and unpaid residual rules. The first duplicates the accepted reader's SQL storage/ownership guards; the second introduces unresolved semantic policy. Prefer one additive module-owned key-read wrapper and a private structural mapper over its already guarded output.

## Contract

Add `(*purchases.Repository).ReadModernBASCandidates(ctx context.Context, organisationID string, expected BASScalarSummary, maximumScalarKeys, maximumScalarBytes, maximumCandidates int64) (*BASModernCandidateDiscovery, error)`. It calls accepted `ReadBASKeys` once, then maps the returned set without further SQL or body reads. A future coordinator uses this instead of a separate purchase key read, after all required shared scalar/body preflight reservations; the wrapper does not itself establish those shared fences.

`BASModernCandidateDiscovery` retains `PhysicalKeys []BASScalarKey` for every accepted family and `Candidates []BASModernCandidateKey` for the modern subset. This preserves the exact physical reservation for later legacy nomination and complete body reconciliation. No legacy root is silently deemed absent from the eventual producer.

`BASModernCandidateKey` contains typed `Kind`, `OrganisationID`, `PostingID`, `DocumentID`, `PaymentID`, `Sequence` and `PostingAllocationSequence`. Kinds distinguish posting fallback, posting allocation, payment fallback and payment allocation. Exact opaque IDs stay structured. A fallback has sequence zero; posting-side keys have no payment ID. A payment allocation preserves its own sequence separately from the referenced posting allocation sequence. No child borrows an ancestor's original provenance or gains a journal-line mapping.

The accepted read establishes all-family count/charge/order and owner/parent/storage guards, including the posting's document existence/ownership. Private mapping requires that guarded document reference and asserts allocation/posting, payment/posting and payment-allocation/payment/posting-allocation links, rather than duplicating all 15 SQL-family predicates. It uses no amount, period, status or current-basis predicate. Sort by kind, posting ID, payment ID and own sequence, preserving posting-allocation linkage. Reject a negative candidate allowance before SQL and enforce the smaller of the caller allowance and 1,000. Zero permits an empty modern subset even when nonmodern physical history exists. Any key-read error, cancellation or candidate overflow returns no discovery object. Preserve the caller transaction; never hydrate financial bodies, begin/commit/rollback, or write revisions.

## Verification

Independently compare exact writer identities, scalar physical history, complete coverage bodies and the existing claim/accounting conservation oracle. Pin payment own sequence versus posting-allocation sequence separately: current writers and complete readers require them to be equal; a synthetic nonidentity mapping fixture proves structural field preservation only. Claiming or deferring an existing source changes its decisions/remainders without adding modern candidates; unrelated legacy/opening/manual history must remain in PhysicalKeys without becoming modern nominees. Opening roots cannot use the evidence-only disposition, which requires a document source.

Use synthetic/count-only zero-child and 1,000/1,001 cases only for structural cardinality, without claiming full-reader financial validity. Test exact/short key/byte/candidate budgets, cancellation, no partial result, read-only caller ownership and complete physical-set retention. Independent specification review precedes quality review. ROOT runs focused and complete affected purchase/reporting native race, excluding only the previously accepted expensive 1,000-public-posting fixture, then existing-route TLS, default Core and pinned production build with independent binary hash verification. No nomination/scalar exclusion is accepted.

Exact legacy nomination/suppression, claim decision precedence, transitive proof representation within 20 identities, raw component persistence encoding, duplicate-fact verification, supported journal-line mapping, shared global fences, source-currentness hashing and the combined producer remain open.
